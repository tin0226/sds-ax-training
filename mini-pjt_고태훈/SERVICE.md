# SERVICE · 가족 1주 식단 Agent

## 1. 사용자·문제·가치
- 누구를 위한 서비스인가: 4인 가족의 끼니를 준비하는 사람 (가족 식단 담당자)
- 어떤 문제를 푸는가: 가족마다 기피 음식·선호 음식·하루 칼로리가 다르고 먹는 끼니도 달라서(예: 아빠는 평일 점심을 안 먹고, 첫째는 주말 아침을 안 먹음) 일주일 21끼를 짜기 번거롭다. 짜다 보면 지난주와 비슷한 상차림이 반복된다
- 지금은 어떻게 해결하나: 머릿속이나 메모로 끼니마다 메뉴를 고르고, 가격·칼로리는 따로 계산하거나 아예 따지지 않는다
- 이걸로 뭐가 좋아지나: 예산과 바뀐 사정을 말하면 기피 음식 0건, 예산·칼로리·중복 조건을 지킨 1주 식단이 끼니별 메뉴와 마지막 주간 이유 요약으로 바로 나온다 (끼니별 상세 이유는 파일로 따로 정리되고, 궁금한 끼니를 물으면 답한다)

## 2. 서비스 확장 관점
- 수익·기여: 밀키트·반찬 배송몰에 붙여 장바구니(1주 식단 = 주문 목록)로 연결하면 주문 단가와 재구매가 오른다. 가족에게는 매주 반복되는 "이번 주 뭐 먹지" 고민과 가격·칼로리 계산 시간을 줄인다
- 규모: 가구당 주 1회 식단 생성 + 일정이 바뀔 때마다 다시 짜기 (가구당 주 2~3회 호출)
- 대체제와 차별점: 식단 앱이나 일반 챗봇은 가족 구성원별 출석·기피를 동시에 맞추지 못하고 합계를 자주 틀린다. 이 에이전트는 최적화 도구가 식단을 짜서 조건 충족을 보장하고, LLM은 요청 해석과 설명만 맡는다

## 3. 사용 예상 도구·데이터
- 도구 (모두 LangChain `@tool`, 에이전트가 호출 / 외부 인터페이스는 `POST /query`)
  - `plan_week`: 1주 식단 짜기. 정수 계획(PuLP + HiGHS)으로 기피·예산·칼로리·중복·반복 조건을 지킨 식단, 해가 없으면 완화안
  - `check_plan`: 식단 조건 독립 재검사 / `weekly_summary`: 주간 이유 요약·끼니별 이유
  - `get_family_info`: 가족 정보 조회(기피는 개수만) / `get_past_plan`: 확정된 지난 식단 조회
  - `save_plan`: 식단 확정 저장(사용자 "예" 승인 후에만 실행) / `search_docs`: 메뉴·가족 문서 RAG 검색(Chroma + Titan 임베딩)
- 상차림 규칙
  - 한 끼 = 주식 1개(밥·떡·면·빵) + 국 1개 + 메인반찬 1개 + 서로 다른 부반찬 3개. 모든 메뉴는 가격·1인분 칼로리·팩당 인분 수가 정해진 완제품
  - 주식·국·메인반찬을 기피하는 사람에게는 같은 종류의 대체 메뉴를 따로 준다. 부반찬은 대체 없이 빼고 먹되, 3개 중 최소 1개는 먹을 수 있어야 한다
  - 최근 3주 식단과 (국, 메인반찬) 조합이 겹치는 끼니는 이번 주 끼니의 절반 이하로 한다
- 데이터 (모두 가짜 데이터, `data/`)
  - 메뉴 목록 CSV: 197개 (주식 16개(밥 3, 떡 5, 면 3, 빵 5), 국 38개, 메인반찬 38개, 부반찬 105개)
  - 가족 프로필 JSON: 4명의 기피·선호 음식, 하루 칼로리 범위, 21끼 출석표, 기본 주간 예산 (읽기 전용)
  - 지난 식단 기록 JSON: 2026-W41~W47 7주치

## 4. 서비스 정책 (가드레일 요약)
- 기피 음식은 어떤 경우에도 그 사람에게 내지 않고, 기피 항목은 건강 정보일 수 있어 응답·근거 문서·검색 DB에 "누가 무엇을 기피하는지"를 드러내지 않는다
- 가족 기본 정보(일정·선호·기피·칼로리·기본 예산)는 조회만 가능하고 변경할 수 없다. 이번 주에만 적용하는 출석 변경·추가로 뺄 음식은 반영하되, 기피를 푸는 것은 이번 주만이라도 받지 않는다
- 메뉴와 금액·칼로리 숫자는 지어내지 않는다. 메뉴는 목록에 있는 것만, 숫자는 도구 결과만 인용하고 LLM이 직접 계산하지 않는다
- 식단 확정(기록 저장)은 사용자가 "확정"이라고 말할 때만 시작하고, "저장할까요? 예/아니오"에 "예"일 때만 저장한다. 지난 주차는 저장하지 않는다
- 조건을 모두 지킬 수 없으면 지어낸 식단 대신 무엇을 얼마나 풀면 되는지 안내한다. 시스템 프롬프트 공개·지시 무시 요청은 거절한다
- 세부 케이스는 `evaluation/test_queries.csv` 의 guardrail·negative 항목에서 검증됨

## 5. 성공 기준
- 인-아웃 세트(`evaluation/test_queries.csv` 30건) 90% 이상 통과를 완성으로 본다
- "쓸만하다" 판단 지표
  - 식단 요청 질문 전부에서 기피 위반 0건, 예산·칼로리·중복·반복 조건 100% 만족 (check_plan 독립 재검사)
  - 답변의 금액·칼로리 숫자 중 도구 결과에 없는 숫자 0건, 기피 정보 누출 0건
  - 조건을 지킬 수 없는 질문에 지어낸 식단 0건
  - 응답 시간 평균 15초 이내 (식단 1회 최적화 포함)
